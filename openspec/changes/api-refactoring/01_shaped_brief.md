## Phase 1: Frame

### Problem Statement
The SNAAPI API Gateway has evolved organically, accumulating technical debt concentrated primarily in the `EditorialOrchestrator` class. This 536-line god class with 19 constructor dependencies handles too many responsibilities: data fetching, async promise management, transformation coordination, error handling, and signature resolution. This makes the code difficult to test, extend, and maintain.

### Desired Outcome
A well-structured, SOLID-compliant orchestration layer where:
- Each class has a single, clear responsibility
- New content types or aggregation patterns can be added without modifying existing classes
- The code is easily testable with focused unit tests
- Error handling follows a consistent, documented strategy
- Data flowing through the system is typed, not raw arrays

### Appetite
Medium-large: 5 vertical slices, each independently deliverable and testable.

### Non-Goals
- Changing the external API contract (response format must remain identical)
- Modifying external client libraries (vendor packages)
- Adding new features or endpoints
- Changing the framework (Symfony 6.4 stays)
- Modifying Docker/CI configuration

## Phase 3: Shape A - Extract and Compose

### A1: InsertedNewsResolver (extracts from EditorialOrchestrator)
**Mechanism**: New service class that encapsulates the logic of fetching inserted news editorials, their sections, signatures, and multimedia. Receives the editorial body, calls external clients, returns typed aggregated data.

### A2: RecommendedEditorialsResolver (extracts from EditorialOrchestrator)
**Mechanism**: New service class that encapsulates recommended editorial aggregation. Similar pattern to A1 but with error-tolerant fetching (catch and skip).

### A3: EditorialResolutionData (Value Object)
**Mechanism**: Typed class replacing `$resolveData` array. Properties: `multimedia`, `multimediaOpening`, `insertedNews`, `recommendedEditorials`, `photoFromBodyTags`, `membershipLinkCombine`. Immutable with builder pattern.

### A4: SignatureResolver (extracts from EditorialOrchestrator)
**Mechanism**: Dedicated service for journalist signature resolution via alias ID. Used by main orchestrator, InsertedNewsResolver, and RecommendedEditorialsResolver (DRY).

### A5: MultimediaResolver (extracts from EditorialOrchestrator)
**Mechanism**: Encapsulates async multimedia fetching, promise settlement, and opening resolution. Manages Guzzle promise lifecycle.

### A6: EditorialOrchestrator (simplified)
**Mechanism**: Becomes a thin coordinator that delegates to A1-A5 services. Constructor deps drop from 19 to ~7 (the extracted services + remaining transformers).

### A7: ErrorHandlingStrategy
**Mechanism**: Interface `SafeExternalCallHandler` with `execute(callable, LoggerInterface): mixed|null`. Two implementations: `LogAndSkip` (for recommended editorials) and `LogAndThrow` (for critical paths).

## Phase 7: Slices

### Slice 1: Extract SignatureResolver + EditorialResolutionData
**Demo**: SignatureResolver resolves journalist aliases. EditorialResolutionData replaces raw array.
**Files**: New `src/Orchestrator/Service/SignatureResolver.php`, new `src/Orchestrator/DTO/EditorialResolutionData.php`
**Tests**: Unit tests for both new classes. EditorialOrchestratorTest updated.
**Risk**: Low (extraction, no behavior change)

### Slice 2: Extract InsertedNewsResolver
**Demo**: Inserted news aggregation handled by dedicated service.
**Files**: New `src/Orchestrator/Service/InsertedNewsResolver.php`
**Tests**: New InsertedNewsResolverTest. EditorialOrchestratorTest updated.
**Risk**: Medium (complex async logic)

### Slice 3: Extract RecommendedEditorialsResolver + MultimediaResolver
**Demo**: Recommended editorial and multimedia aggregation in dedicated services.
**Files**: New `src/Orchestrator/Service/RecommendedEditorialsResolver.php`, new `src/Orchestrator/Service/MultimediaResolver.php`
**Tests**: New tests for both. EditorialOrchestratorTest simplified.
**Risk**: Medium (promise handling)

### Slice 4: Simplify EditorialOrchestrator + ErrorHandlingStrategy
**Demo**: EditorialOrchestrator reduced to thin coordinator. Consistent error handling.
**Files**: Modified EditorialOrchestrator, new ErrorHandlingStrategy interface.
**Tests**: EditorialOrchestratorTest dramatically simplified. Integration-level validation.
**Risk**: Medium (final integration)

### Slice 5: Flatten Transformer Hierarchy (Optional)
**Demo**: Body transformers use composition (traits) instead of deep inheritance.
**Files**: Modified body transformer classes.
**Tests**: All existing transformer tests pass unchanged.
**Risk**: Low-Medium (many files but simple pattern)
