## Phase 1: Frame

### Problem Statement
The SNAAPI API Gateway's `EditorialOrchestrator` (536 lines, 19 constructor deps) mixes two fundamental concerns: **data aggregation** (async fetching from 7+ microservices) and **data presentation** (serializing to mobile app JSON format). No domain model exists between these two responsibilities - data flows directly from HTTP clients through "Apps" transformers to `array<string, mixed>`.

This tight coupling makes it impossible to:
- Support different output formats (web, AMP, RSS, push notifications)
- Test aggregation logic independently from presentation
- Reuse the aggregated data for different consumers

### Desired Outcome
A clean two-layer architecture where:
1. **Aggregator layer** fetches and resolves all external data into a typed, immutable domain aggregate (`ResolvedEditorial`)
2. **Presenter layer** translates the aggregate into format-specific JSON via a Strategy/Registry pattern
3. New output formats are added by implementing `EditorialPresenterInterface` (OCP)
4. This pattern becomes the **mandatory product standard** for all future features

### Appetite
8 vertical slices, each independently deliverable and testable.

### Non-Goals
- Changing the external API contract (response format must remain identical)
- Modifying external client libraries (vendor packages)
- Modifying the 30+ existing DataTransformer classes (reused by AppsEditorialPresenter)
- Adding new features or endpoints
- Changing the framework (Symfony 6.4 stays)

## Phase 3: Shape A - Aggregator-Presenter Architecture

### A1: ResolvedEditorial (Domain Aggregate DTO)
**Mechanism**: Immutable `final readonly class` containing ALL resolved data from external services. Properties: editorial, section, tags, signatures, multimedia, multimediaOpening, insertedNews (typed array), recommendedEditorials (typed array), photoFromBodyTags, membershipLinks, commentCount.

Sub-DTOs: `ResolvedInsertedNews`, `ResolvedRecommendedEditorial` for typed nested data.

### A2: EditorialAggregator (Aggregation Layer)
**Mechanism**: Service that orchestrates all external service calls, resolves async promises, and returns `ResolvedEditorial`. Delegates to sub-services:
- `SignatureResolver` - journalist alias resolution (shared by main, inserted, recommended)
- `InsertedNewsResolver` - inserted news aggregation
- `RecommendedEditorialsResolver` - recommended editorial aggregation
- `MultimediaResolver` - async multimedia fetching + promise settlement

### A3: EditorialPresenterInterface + Registry (Presentation Layer)
**Mechanism**: Interface with `present(ResolvedEditorial): array` and `supports(string $format): bool`. Registry selects presenter by format string. New formats = new implementations.

### A4: AppsEditorialPresenter (Current Format Implementation)
**Mechanism**: Implements `EditorialPresenterInterface` for format 'apps'. Reuses ALL existing DataTransformer classes (DetailsAppsDataTransformer, BodyDataTransformer, StandfirstDataTransformer, etc.) without modification.

### A5: EditorialPresenterCompiler (Symfony DI Integration)
**Mechanism**: Compiler pass that collects services tagged `app.editorial.presenter` and registers them with the `EditorialPresenterRegistry`. Same pattern as existing `BodyDataTransformerCompiler`.

### A6: Simplified EditorialOrchestrator
**Mechanism**: Reduced to ~50 LOC thin coordinator: aggregate(id) → present(resolved, 'apps'). Constructor deps drop from 19 to ~4.

## Phase 7: Slices

### Slice 1: ResolvedEditorial DTO + SignatureResolver
**Demo**: Typed domain aggregate exists. SignatureResolver resolves journalist aliases.
**New files**: `Aggregator/DTO/ResolvedEditorial.php`, `ResolvedInsertedNews.php`, `ResolvedRecommendedEditorial.php`, `Aggregator/Service/SignatureResolver.php`
**Tests**: Unit tests for DTOs and SignatureResolver
**Risk**: Low (additive only, no existing code changes)

### Slice 2: EditorialAggregator + sub-services
**Demo**: Full aggregation pipeline produces ResolvedEditorial from external services.
**New files**: `Aggregator/EditorialAggregatorInterface.php`, `EditorialAggregator.php`, `Service/InsertedNewsResolver.php`, `Service/RecommendedEditorialsResolver.php`, `Service/MultimediaResolver.php`
**Tests**: Unit tests for each service
**Risk**: Medium (complex async logic extraction)

### Slice 3: EditorialPresenter + AppsEditorialPresenter
**Demo**: Presenter takes ResolvedEditorial and produces identical JSON as current system.
**New files**: `Presenter/EditorialPresenterInterface.php`, `EditorialPresenterRegistry.php`, `Presenter/Apps/AppsEditorialPresenter.php`, `Compiler/EditorialPresenterCompiler.php`, `config/packages/presenters.yaml`
**Tests**: Unit tests verifying output matches current format exactly
**Risk**: Medium (must produce byte-identical output)

### Slice 4: Integrate and simplify EditorialOrchestrator
**Demo**: EditorialOrchestrator is ~50 LOC, delegates to aggregator + presenter.
**Modified**: `EditorialOrchestrator.php`, `EditorialOrchestratorTest.php`, `config/packages/aggregator.yaml`
**Tests**: Full suite passes, API responses identical
**Risk**: Medium-High (integration point, backward compatibility critical)

### Slice 5: Resilience - Circuit Breaker + ServiceCriticality
**Demo**: Each Aggregator sub-service degrades gracefully based on service criticality.
**New files**: `Infrastructure/Enum/ServiceCriticality.php`, tests for degradation scenarios
**Modified**: All Aggregator/Service/ resolvers to include try/catch with criticality policy
**Tests**: Unit tests for each degradation scenario (CRITICAL fail, LOW degrade)
**Risk**: Medium (must preserve existing behavior for happy path)

### Slice 6: httplug Cache + Couchbase Configuration
**Demo**: All external HTTP calls cached transparently via httplug.
**New/Modified**: `config/packages/httplug.yaml`, Couchbase PSR-6 adapter config
**Tests**: Integration test verifying cache hit/miss behavior
**Risk**: Medium (infrastructure change, needs testing with all clients)

### Slice 7: Reactive Invalidation - AMQP Handlers
**Demo**: Content changes in microservices trigger cache invalidation in SNAAPI.
**New files**: `Message/SectionUpdated.php`, `MessageHandler/SectionUpdatedHandler.php`, etc.
**Modified**: `config/packages/messenger.yaml` (routing for new events)
**Tests**: Unit tests for each handler verifying correct cache key invalidation
**Risk**: Low (additive, uses existing Messenger infrastructure)
**Reference**: Existing `PurgeEditorialHandler` as implementation pattern

### Slice 8: Document as product standard
**Demo**: Pattern documented in openspec/, CLAUDE.md, architecture profile.
**New/Modified**: `aggregator-presenter-pattern.yaml`, `CLAUDE.md`, `architecture-profile.yaml`, `project-profile.md`
**Risk**: Low (documentation only)
